# 6. 기능별 Claude Code 작업 프롬프트

아래 작업은 순서대로 실행한다. 현재는 작업 01부터 시작한다. 각 프롬프트는 한 세션의 범위이며 이전 작업의 미완료 항목이 있으면 먼저 정리한다.

## 모든 작업에 붙일 공통 지침

> CLAUDE.md와 이번 작업에 관련된 설계·현재 코드를 먼저 읽어라. 기존 변경을 보존하라. 구현 전에 범위와 인수 조건을 짧게 적고, 한 기능의 실제 동작까지 완성하라. 게임 규칙은 domain, 실행 흐름은 application, UI는 presentation에 둬라. 테스트와 실제 실행을 수행하고 실행한 명령·결과·미실행 항목을 구분하여 보고하라. 관련 문서와 주간 기록을 갱신하라. 새 라이브러리나 엔진 변경은 필요성을 검증하고 버전을 기록하라. 이번 범위 밖의 시스템과 미래용 빈 매니저는 만들지 마라.

## 작업 01 — 첫 Godot 실행 빌드

> Godot 4.x 설치 상태를 확인하고 사용 가능한 안정판의 정확한 버전을 docs/production/toolchain.md에 기록하라. project.godot, 진입 씬, 임시 타일/도형으로 된 작은 마을, Player를 만들어 WASD 이동과 벽 충돌을 구현하라. 플레이어 시작점과 충돌 경계를 데이터/씬에서 편집할 수 있게 하라. 장부·경제·NPC는 아직 만들지 마라. headless import와 실제 게임 창을 실행하여 이동·충돌·종료를 확인하라. 엔진 실행이 불가능하면 설치 상태와 필요한 조치를 구체적으로 기록하고 실행 성공을 주장하지 마라. 수락 기준: 오류 없는 시작, 프레임률과 무관한 이동, 벽 관통 없음, 정상 종료.

## 작업 02 — 상호작용과 아이템 수집

> 작업 01의 빌드에 상호작용 대상 선택과 E 프롬프트를 추가하라. 근처 나무에서 목재를 얻어 24슬롯 가방에 넣도록 하라. ItemDef와 InventoryState를 분리하고 UI는 명령만 호출하게 하라. 나무별 당일 획득 상태를 보존하라. 수락 기준: 범위 밖 채집 불가, 반복 입력으로 중복 획득 없음, 가방이 가득 차면 자원이 사라지지 않음, 선택 대상의 이름이 표시됨. 의뢰·건설은 제외하라.

## 작업 03 — 달력·일시 정지·저장 v1

> 06:00~22:00 시계, 14일 계절, 56일 연도와 하루 종료 진입점을 추가하라. 아직 경제 tick은 없지만 DayRunner의 일자 중복 방지 경계를 정의하라. 메뉴를 열면 시계와 월드가 멈추게 하라. WorldState에서 플레이어 위치·시각·가방·채집 상태를 JSON으로 저장하고 검증 후 불러와라. 수락 기준: 저장 왕복 동일성, 14/42/56일 경계, 파싱 실패 시 현재 상태 보존, 임시 파일 손상 때 유효 저장 보존. tests/run_tests.gd 실행기를 이 작업의 실질적인 상태 검증에 필요한 최소 범위로 만들어라.

## 작업 04 — 하루 생산과 소비

> GDD 생산 기준과 data/design/economy-baseline.json을 읽고 런타임 정의를 생성하라. 설계 검증 파일을 게임 코드에서 직접 임포트하지 말고 런타임 RecipeDef/BuildingDef 스키마에 맞춰라. 농장·벌목장·제분소·빵집과 24명 소비를 DayRunner에 연결하라. 입력→가공→소비 순서를 고정하고 원료 부족·창고 부족·인력 부족 원인을 보고하라. 수락 기준: 정상 밀32→빵40→순식량+16, 겨울 순식량-14, 투입 부족 시 음수 없음, 결산 이중 실행 없음. 시뮬레이션 결과를 장부 임시 UI에서 확인하라.

## 작업 05 — 같은 문제를 직접 해결하거나 위임

> 파손 제분소, 토마의 대사, 목재8·작업4의 수리 프로젝트를 구현하라. 직접 수리 4회와 노동자1명·2일 위임이 동일 ProjectState를 완료하게 하라. 예약 물자, 진행 중 취소, 완료 후 재요청을 처리하라. UI에서 직접/위임 비용과 생산 재개 날짜를 설명하라. 수락 기준: 어느 경로든 동일 제분소 활성화, 재료/보상 한 번만 처리, 담당자의 이중 배치 거부, 로드 후 진행량 유지, 파손/복구 외형 및 토마 대사 변화.

## 작업 06 — 장부와 첫 30분

> 현황·생산·주민·위임·연대기 탭의 필요한 최소 내용을 만들고, 현재 식량과 부족 원인에서 제분소/토마를 지도 추적할 수 있게 하라. 첫 30분 시나리오를 디버그 명령 없이 완료하게 하라. 일일 결산에 생산/소비/병목을 따로 표시하라. 수락 기준: 장부와 월드 상태 일치, 메뉴 일시 정지, 수리 뒤 대사·시설·빵 재고 변화, 입력 반복으로 중복 결산 없음. 아직 준비하지 못한 콘텐츠를 완료된 것처럼 표시하지 마라.

## 작업 07 — 주민·세금·시장

> 먼저 주민 직무와 인력 배치만 한 작업으로 구현하고 검증하라. 이후 별도 작업으로 세금/유지비, 그다음 시장 거래를 구현하라. 각 단계마다 테스트·실행·기록을 마친 뒤 진행하라. 주민24명 중 노동 가능12명과 6가구를 일관되게 유지하라. 세금은 가구, 식량은 인구를 기준으로 한다. 거래는 방문일·재고·매입 한도·단가·예약 수량을 검사한다. 수락 기준: 음수 재고 없음, 미납 유예/휴업/복구 동작, 거래 취소 보존, 신뢰 변화 원인 표시.

## 작업 08 — 겨울 캠페인과 엔딩

> 기존 생산·소비를 바꾸지 않고 계절 계수와 겨울 비축 안내를 연결하라. GDD의 자립 조건을 상태 질의로 구현하고 최근7일 식사/미납 이력을 저장하라. 연대기 회고와 재건 축제, 계속 플레이를 추가하라. 수락 기준: 겨울14일을 건너뛰지 않음, 자립 조건 하나라도 빠지면 이유 표시, 조건 충족 보상 한 번, 로드 후 판정 동일, 엔딩 뒤 진행 가능. 플레이 시간과 체감 난이도는 직접 테스트 기록으로 남겨라.

## 이후 콘텐츠 작업 양식

> 추가할 콘텐츠: [건물/인물/의뢰/사건 한 가지]. 핵심 재미 기여: [플레이어의 어떤 선택이 바뀌는지]. 기존 데이터 스키마를 먼저 확인하고 가능하면 코드 수정 없이 추가하라. 신규 ID·해금 조건·입력/출력·비용·직접/위임 연결·실패/취소·세이브 영향을 명시하라. 데이터 검증과 실제 획득/완료 경로를 실행하고 화면·대사·장부 중 필요한 결과를 확인하라. 스키마 변경이 필요하면 기존 콘텐츠 회귀와 마이그레이션 계획을 함께 작성하라.

## 버그 수정 작업 양식

> 증상: [관찰]. 재현 빌드/저장: [경로]. 재현 단계: [최소 단계]. 기대 결과: [규칙]. 먼저 재현하고 원인을 좁혀라. 최소 수정 후 원래 재현과 관련 경계 사례를 확인하라. 경제/저장 버그는 같은 문제를 잡는 회귀 테스트를 추가하라. 재현하지 못했다면 추측으로 큰 리팩터링을 하지 말고 필요한 로그와 확인 결과를 남겨라.
