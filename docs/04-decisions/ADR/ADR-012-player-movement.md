# ADR-012: 생활 이동의 최소 구현 경계

## 상태·날짜

Proposed, 2026-10-31. IH-101 구현 준비용 기준안. 사용자 확정 기술 ADR-011은 그대로 유지한다. 구현·기술 검증 및 사용자 GUI 확인은 완료했다. 최종 조작 정책/수치 결정은 남아 있으므로 Proposed를 유지하며 Accepted로 보고하지 않는다.

## 배경

첫 생활 조작은 자유롭게 걷고 주변 장애물을 돌아가는 감각을 검증해야 한다. 향후 상호작용·수집·전투가 추가되더라도 이동 스크립트가 모든 규칙을 소유해서는 안 된다. 초기 제안 당시에는 게임플레이 구현이 없었다. 이후 구현 결과는 아래 후속 기록에 보존한다.

## 검토한 대안

- Node2D 직접 좌표 이동: 충돌·미끄러짐을 별도로 구현해야 함.
- RigidBody2D: 물리 힘 기반 반응이 주목적이며 즉시 반응하는 생활 조작의 첫 검증 범위를 늘림.
- CharacterBody2D floating: Godot의 충돌/미끄러짐을 활용하고 이동 의도와 결과를 분리 가능.
- 타일 단위/4방향 이동: 좁은 이동 규칙에는 적합하나 자유 생활 이동의 대각선 조작을 제한함.
- 복합 상태머신/Autoload 이동 서비스: 단일 Player의 idle/walk에는 불필요한 의존성.

## 제안 결정·이유

CharacterBody2D + 물리 틱 이동,8방향 정규화된 최대 속도,4방향 표현을 제안한다. 짧은 controller와 수동 Visual 어댑터로 나누고 카메라·검사 지형은 씬으로 구성한다. 전역 Input 폴링과 별개로 조작 게이트/포커스 복귀 정책을 명시한다. 장래 행동/아이템 도메인은 Player에서 분리한다.

속도96,화면640×360,충돌 반지름6 등은 임시 검사 설정이며 최종 게임 수치가 아니다. 구체 계약은 [PLAYER_MOVEMENT](../../02-technical-design/PLAYER_MOVEMENT.md)에 단일 기준으로 둔다.

## 단점·고려사항

즉시 출발·정지의 감각,대각선 facing 가로 우선,카메라 보간 없음은 실제 조작 확인이 필요하다. 4방향 아트로8방향 이동을 표현할 때 어색함이 있을 수 있다. 키보드만 검증하며 게임패드·접근성 설정은 후속이다. 테스트 지형/도형은 제품 아트를 대체하지 않는다.

## 영향·검증

[IH-101 수락 검사](../../03-development/IH-101-ACCEPTANCE.md)의 실제 결과를 근거로 상태를 재검토한다. main_scene은 Foundation 유지,테스트 맵 명시 실행으로 기존 smoke의 의미를 보존한다. 구현은 Claude Code 담당, Codex는 이번에 문서만 작성한다. 기존 ADR을 삭제하거나 엔진 선택을 다시 열지 않는다.

## 구현 검증 결과 (2026-10-31)

Claude Code가 이 제안대로 구현했고 AC-01~12 자동/수동 검사를 통과했다([검증 기록](../../03-development/IH-101-VALIDATION.md)). 상태는 **Proposed 유지**다. 구조(CharacterBody2D floating, controller/Visual 분리, 게이트+neutral 정책)가 고정 엔진에서 동작함을 확인했지만 Accepted 전환과 수치 확정은 별도 결정이다.

검토 항목: ① floating 벽 미끄러짐이 투영 속도가 아닌 거의 전체 속도(약96 u/s)로 진행된다. ② macOS 시작 시 포커스 알림이 `_ready` 이전에 온다(BUG-001에서 처리). ③ 사용자 GUI 확인에서 즉시 출발·정지와 대각 facing 가로 우선에 대한 문제 보고는 없었다. 조작감 평가는 단일 사용자의 짧은 확인이며 플레이테스트 표본이 아니다.
